# Keep or Trash: Evidence-Based Proposal

Prepared for Vission Cooper, Set Up Your Place LLC.
Basis: 161 live edge functions mirrored verbatim, cross-referenced against front-end call sites, inter-function calls, and live database row counts.
Nothing has been deleted. Every item below is a proposal awaiting your decision.

---

## The finding that changes the triage

**`pg_cron` is not installed on the production database.** Only `pg_net` is present. There is no scheduler.

Every function I flagged as a dangerous scheduled job has been sitting inert. The database confirms this rather than merely implying it — the tables those jobs would have written to are empty.

This is why several of my earlier warnings dissolve below. You were right to expect it.

---

## Group A — Delete. Never used, and carries a live defect.

These have zero rows in the tables they write to, zero front-end call sites, and no scheduler to trigger them. Deleting each one removes a documented defect at the same time.

**`weekly-market-data-refresh`** — Invents every market figure it produces, then would push fabricated regulation alerts to investors. Evidence it never ran: no row in `market_data_snapshots` carries its `data_source` value; `market_shift_alerts` is empty; `investor_notifications` of type `market_alert` is empty. Deleting this removes the worst truth-integrity defect on the platform.

**`scheduled-report-generation`** — Emails clients a PDF market report whose rental rates, occupancy and ADR are generated by a model with no data access. `report_generation_logs` is empty; it has never run. Its deal lookup is also broken (matches `'Austin, TX'` against a `city` column holding `'Austin'`), so even the one real section would have been empty.

**`monitor-regulation-feeds`** — Hardcoded stale search strings, 10-city substring matching, no dedupe. `regulation_alerts` is empty; it never produced anything.

**`process-followups`** — The executor is a stub that returns "no pending followups" without reading anything. See Group C: this one has a real cost and needs a replacement decision, not just deletion.

**`env-probe`** — Retired diagnostic, already returns HTTP 410. Safe to remove from the dashboard.

**`upload-digital-product`** — No authentication, `created_by` defaults to `'admin'`, and it doesn't upload anything — it stores a caller-supplied URL verbatim. `digital_products` is empty. Never used.

**`track-download`** — Only exists to track downloads of digital products. Nothing to track. Also writes duplicate rows into `leads` with no dedupe.

## Group B — Delete after confirming the feature is genuinely abandoned

Unused today, but these represent product decisions rather than mistakes. Confirm you don't intend to revive them.

**`seller-document-upload`** — `seller_listing_documents` is empty. It also validates file type from a caller-supplied string rather than the bytes, and its delete authorization checks whether `investor_id` appears as a *substring* of the path. If the seller marketplace is coming back, this needs rebuilding rather than reviving.

**`submit-resident-request` and `manage-resident-portal`** — `residents` has 1 row. The resident portal is effectively unused. It carries two real defects: the intake form returns an existing resident's `access_token` to anyone who submits that email address, and `operator_message` lets any caller post as any operator. Low urgency at one resident; do not promote this feature until both are fixed.

**`penny-landlord-chat`** — In the repo, not deployed live. Decide: deploy, or delete from the repo.

## Group C — Keep, but broken and costing you something now

**`process-followups` — the one with real cost.** There are **5 follow-up rules** in the database. Your staff built them through the UI, saw them save, and reasonably believe automated follow-ups are going out. They are not, and never have been. The CRUD half works; the executor does nothing.

Two honest options: build the executor, or remove the follow-up UI so nobody believes in a system that doesn't exist. Leaving it as-is is the only unacceptable choice. Worth asking your success team directly whether they've been relying on it.

**`send-investor-invitation` — the busiest thing you own.** 9,544 invitation records. It also contains the entire AM certification programme and the AM Service Agreement e-signature.

Two defects that matter at this scale. First, `sign_agreement` has **no authentication**, and its audit trail (`signature_ip`, `user_agent`) is taken from the request body, then hashed — so the signature hash certifies attacker-controlled data. There are **9 agreements, 5 signed**. These are executed commission agreements. Second, `update_trainee_progress` accepts pillar counts from the request body with no identity check, and auto-flips `yp_certified` and `commission_split: 100`. Staff can self-promote to a full commission split. Three staff are currently certified.

**`process-acquisition-payment`** — Sends customer receipts with the wrong legal entity, wrong address, and a support email on a dead domain. The correct block already exists inside `send-acquisition-emails`: Set Up Your Place LLC d/b/a Access Your Place (a Cooper Family Inc. Company), 1150 NW 72nd Ave, Tower I, Suite 455, Miami, FL 33126. Copy it; don't write a third version.

**`stripe-webhook`** — No signature verification at all. Called by Stripe, not by your code, so it looks orphaned in a reference scan. It is not. Keep and fix.

**`twilio-sms-webhook`** — Accepts but never validates Twilio signatures. Note that `sms_logs` is empty: no SMS has ever been sent, which is why the dead `databasepad.com` callback URL never caused visible harm.

**`manage-sop-repository`** — Permissions derive from a `user_role` **string in the request body**, substring-matched. Any caller can pass `"admin"` and create, edit or delete any SOP. Also: 8 SOP rows still contain the retired Ocean307 phrase.

## Group D — Consolidate. Multiple functions doing one job.

**Five property-write paths:** `new-deal-create`, `create-deal`, `create-property`, `add-property`, `am-submit-deal`. Pick one canonical path. Penny needs a single "list a deal" route, not five with different defaults. Note `new-deal-create` silently defaults `acquisition_fee` to 2,500.

**Four writers into `blog_articles`:** `sync-static-articles` (skips on slug collision), `publish-scheduled-articles` (upserts, overwriting), `update-article-status`, `research-and-generate-articles`. Two take opposite actions on the same collision. Lower urgency than it looked — `draft_articles` is empty and `blog_articles` hasn't changed since December 2025 — but settle it before Penny authors anything.

**Two deal-alert paths:** `notify-matching-investors` and `send-inquiry-notifications`' `deal_alert` action. Keep the first; it is reference quality.

**Two photo buckets:** `upload-deal-photo` writes to `property-photos`; `process-property-photos` writes to `digital-products` under a `property-photos/` prefix. Both serve public URLs while `property-photo-urls` tries signed URLs first. One decision needed on bucket privacy.

**Two investor tables:** most functions read `investors`; `send-bulk-email` and `scheduled-report-generation` read `investor_profiles`. Verify which is authoritative.

**Eight sender addresses:** notifications@, marketplace@, support@, noreply@, invitations@, deals@, reports@, plus the wrong setup@rentalnarbitrage.com. Seven legitimate, one error. Consolidate deliberately.

**Two AI stacks:** Penny runs `gpt-4o` on OpenAI. Four functions run `gemini-2.5-flash` through a `fastrouter.io` gateway — `staff-deal-search`, `process-property-photos`, `scheduled-report-generation`, `research-and-generate-articles`. Two of those four are in the delete list, which shrinks the problem.

## Group E — Fix in place, no deletion

**`process-property-photos`** — Does not process anything. Bytes are uploaded unmodified, then marked `is_processed: true`. The AI step only *asks* whether identifying text is visible and records the answer without acting on it. Given your rule that addresses stay confidential until the fee is 50% funded, this is a privacy control that looks implemented and is not.

**`send-bulk-email`** — No unsubscribe link and no opt-out check. `send-acquisition-emails` already has the right pattern in `shouldSendEmail()`. Copy it before any bulk send.

**`staff-deal-search`** and **`manage-portfolio-performance`** — Both fabricate on failure. Make the fallback fail loudly or label itself unmeasured.

**`send-acquisition-emails`** — Receipt amount is derived as `(acquisition_fee || 499) * 100` rather than read from Stripe. A receipt should state the captured amount.

**Dead notification path:** `send-acquisition-emails` calls `sendSMS()` with `investor_id` / `template_key` / `template_data`, but `send-sms-notification` accepts only `to` and `message` and returns 400 without them. Invoice SMS has never sent.

## Suggested sequence

1. Delete Group A. Seven functions, zero usage, removes the worst defects outright.
2. Decide Group B. Three features to confirm abandoned.
3. Fix the two that are costing you now: the e-signature authentication and the follow-up executor.
4. Correct the receipt entity in `process-acquisition-payment`.
5. Consolidate Group D — property writes first, since Penny needs one route.
6. Then start the Penny wiring described in the capability evaluation.

Deleting first is deliberate. Roughly a third of the open findings live in code that has never been used.
