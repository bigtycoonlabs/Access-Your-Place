# Security findings, 6 August 2026

Found during a bug sweep. All closed the same day. Written down because the pattern
matters more than the individual functions.

## Critical: the whole database was writable with the publishable key

`ayp_delete(p_table text, p_filter jsonb)` was `SECURITY DEFINER` and callable by `anon`.

The publishable (anon) key ships inside the front-end JavaScript. Anyone who opened the
website could read it.

The function body builds:

    DELETE FROM "prj_X-ZoVQv6LKXT".<any table> WHERE <any filter> RETURNING *

and executes it as the definer. There is no allow-list of tables, no auth check, and no
guard of any kind. **An empty filter produces an unqualified DELETE.** Properties,
investors, staff_users, everything.

Same shape, same exposure:

- `ayp_insert(table, data)` — write any row to any table
- `ayp_update(table, data, filter)` — modify any row in any table
- `ayp_read(...)` and `ayp_query(...)` — read any table, which includes `password_hash`
  and `session_token` on every account
- `penny_grant_credit(investor_id, amount, ...)` — mint credits. Credits buy deals and
  property leads, so this is money
- `leadforge_grant_credits(...)` — same
- `rls_auto_enable()` — change row-level security

## The wider sweep

52 `SECURITY DEFINER` functions were callable by `anon` in total. Beyond the generic ones
above, the writes included `penny_set_inquiry_status` (move any deal inquiry to any
status), `penny_add_portfolio_property` (add holdings to an investor's portfolio),
`penny_record_payment_submission` (record that a payment was made),
`penny_onboard_landlord`, `penny_upsert_community_update`, and `penny_express_interest`
(create inquiries — a spam vector at minimum).

The reads included `penny_check_account`, `penny_find_client`, `penny_client_activity`
and `penny_lookup_account`, all of which expose client records.

## What was done

Every `SECURITY DEFINER` function in `public` was revoked from `public`, `anon` and
`authenticated`, and granted to `service_role`.

**Nothing legitimate lost access.** This was verified before acting, not assumed: a grep
of the entire front end found that **the browser calls no RPCs directly**. Every one is
invoked from an edge function, and edge functions run as `service_role`.

Confirmed after: 59 `SECURITY DEFINER` functions, 0 callable by `anon`, 59 callable by
`service_role`. `penny_live_deals` still returns 18, `penny_marketplace_listings` 21,
`penny_open_inquiries` 4, `ayp_sources_for_market('Austin','TX')` 12.

## What could not be determined

**Whether any of this was ever exploited.** There is no audit trail on RPC calls. Row
counts look normal — 21 properties, 34 investors — but only the owners know what should
be there.

## Actions for the owners

1. **Rotate the Supabase keys.** Cheap insurance against a window that cannot be audited.
2. **Review `properties`, `investors` and `investor_credits`** for anything unfamiliar.
3. Close the live Stripe account; `PaymentCheckout.tsx` still hardcodes a live
   publishable key.

## The rule this produces

A `SECURITY DEFINER` function bypasses row-level security by design. On this project it
must be granted to `service_role` only, unless there is a specific, written reason a
browser needs it.

Postgres grants `EXECUTE` on new functions to `PUBLIC` by default, so **a new function is
exposed the moment it is created unless the migration revokes it.** Revoking from `anon`
alone is not enough — `anon` inherits through `PUBLIC`. Revoke from `public` explicitly,
then verify with `has_function_privilege`. A migration reporting success proves nothing
about permissions.

# Second sweep, later the same day

Every view created AFTER the first sweep had inherited the same default write grants. The
hole reopens every time a view is made, which is why it is written down as a rule rather
than a one-time fix.

## Found and closed

**`penny_memory` — writable by anon, and this was the worst of them.** Penny's memories are
injected into her system prompt on every turn. Write access for anyone holding the
publishable key is therefore a **prompt-injection channel**: you could write a "memory" and
have Penny carry it as something she knows and act on. That is worse than data tampering,
because the tampering speaks for itself afterwards. Now fully closed to anon, read as well
as write.

**`payment_requests` — writable by anon.** Anyone could mark a payment request paid, or
invent one. Fully closed.

**`ayp_pricing` — writable by anon.** Anyone could change what every deal costs. Read stays
open because prices are public; write is closed.

**`leads` — writable by anon.** Anyone could delete inbound leads, which is the constraint
of the business. Write closed. Read stays because `StaffDashboard` reads it directly.

**`properties` — DELETE by anon.** The marketplace itself was deletable by anyone who
opened the website.

## The properties decision, and its honest tradeoff

The two staff delete flows already carried a soft-delete fallback: if the hard delete
errors they set `status='deleted', is_published=false` instead. So revoking DELETE does not
break the feature — it makes the fallback fire, turning an irreversible browser-initiated
delete into a reversible one. Better behaviour regardless, and consistent with the owner's
call on the mass-delete button.

**The tradeoff, recorded rather than hidden:** those flows also try to delete child rows
(`property_photos`, `deal_analytics` and similar), each wrapped in try/catch and ignored.
Those now silently fail and leave orphaned children. Orphaned rows are a tidiness problem;
a deletable marketplace is a business-ending one.

`service_role` keeps DELETE, so a genuine hard delete is still possible from an edge
function when one is actually wanted.

## Still open, stated plainly

`properties` remains **UPDATE-able by anon**, because 16 legitimate staff writes go through
the browser. Closing it means moving those writes into edge functions — real work, not a
grant change. Until then, anyone with the publishable key can modify a listing.

That is the largest remaining exposure on the platform and it should be scheduled.

## Verified after

All 30 RPCs Penny depends on still exist and are still callable by `service_role`. Nothing
revoked broke her.

# Third sweep: credentials readable by anon

## Found

`public.landlord_contacts` exposed **`password_hash`, `session_token` and `reset_token`**
to anon.

Zero rows today, so nothing has leaked. But `/list-your-property` and `landlord-auth` now
create these accounts, so **the first landlord signup would have published a credential
hash and a live session token** to anyone holding the publishable key.

The session token is the worse of the two: readable means account takeover with no cracking
required. The reset token is close behind — it is a password change.

No other table on the platform exposes a credential column to anon. That was checked, not
assumed.

## The mistake I made fixing it, because it is the more useful lesson

My first fix removed the credential columns from the view.

**That broke landlord authentication.** `landlord-auth` reads `password_hash`,
`session_token` and `reset_token` through PostgREST, which resolves to the public view. With
the columns gone, login, password reset and session verification would all have failed —
silently, with a 400 nobody would have connected to this change.

**That is exactly the defect that made Penny blind for her entire existence**: a column
present on the table and missing from the view. I reintroduced it while fixing something
else, an hour after documenting it as the trap to avoid.

It was caught by asking a second question. Not "is the secret hidden?" — which was true —
but **"can the thing that needs this column still read it?"** Only the second question finds
this.

## The correct tool

**Column-level grants.** The view carries every column, so `service_role` reads what it
needs. `anon` is granted `SELECT` on the safe columns only. Asking for `password_hash` as
anon is now a permission error rather than a leak.

Verified across nine checks: `service_role` can read hash, session and reset token; `anon`
can read none of them; `anon` can still read `id`, `portal_enabled` and `assigned_am_id`,
which is what `StaffDashboard` counts.

`DROP VIEW ... CASCADE` was used, so dependents were checked afterwards:
`penny_onboard_landlord`, `penny_new_landlord_inquiries` and `penny_mark_landlord_welcomed`
all survive.

## Rule

Hiding a column from one reader by deleting it for every reader is not a fix, it is a
different outage. Use column-level grants, then verify BOTH directions: the attacker cannot
read it, and the legitimate consumer still can.

# Fourth sweep

## Anon write access: 36 views down to 6, and zero DELETE anywhere

36 public views were writable by anyone holding the publishable key. Grepping the front end
for `.from('<table>').insert/update/upsert/delete` found that **only five are written by the
browser**: `error_logs`, `investor_notifications`, `investor_portfolio`, `property_photos`,
`staff_notifications`.

The other 31 had no legitimate browser write at all. The ones that mattered most:

- **`penny_directives` and `penny_operator_memory`** — these shape how Penny *behaves*.
  Anon write is a **prompt-injection channel**: write a directive and she carries it as
  something the company told her.
- **`investor_credit_transactions`** — credits buy deals, so this is money.
- **`investor_portfolio`** — someone's holdings.
- **`penny_escalations`** — a client's escalation could be deleted and simply vanish from
  the queue.
- **`corporate_applications`, `landlord_documents`, `landlord_messages`** — the supply
  side's private correspondence.

All 31 revoked. The five the browser needs keep INSERT and UPDATE but **lose DELETE** —
nothing in those flows deletes, and an anon DELETE on `investor_portfolio` would wipe a
client's holdings.

**Result: 0 tables anon can DELETE. 6 anon can write, all verified as needed.**

Reads left alone deliberately: staff screens authenticate through a custom session and read
these as anon. Breaking every staff screen to close a write hole would be a bad trade — that
needs the session work, not a grant change.

## Data quality on the client file import

- **16 records had `has_llc` set to the word "Whether"** — the first word of the form
  *question*, captured as though it were the answer. Penny reading "their LLC status is
  Whether" is a small lie in a confident voice, which is this platform's signature failure.
  Set to null: we do not know is the honest value.
- 25 records have no contact name, but **all 25 have a company**, so nobody is
  unidentifiable. Left as-is rather than inventing a person's name from an email local-part.
- 0 malformed email addresses out of 475.
- 4 phone numbers are not 10 or 11 digits. Left alone — a staff member can fix a typo, and
  guessing at a phone number is worse than showing the odd one.

# Fifth sweep: the duplicate client list

## The clash

`legacy_masterspaces_intake` held **437 rows** — the same Master Spaces intake list, loaded
previously. All **424** of its distinct emails also exist in `client_files`, and **none are
unique to it**. A complete subset.

Two tables holding the same people is a real operational problem: staff trust whichever one
they happened to open, and Penny would have had to choose between them.

## What was rescued before retiring it

Two fields existed only in the legacy table:

- `prior_consultant` — 6 rows
- `sms_opt_in` — 41 rows

**`sms_opt_in` is not what its name says.** Its values are "Nonmember" (16), "Member" (12),
"Yes" (7), "No" (3), "Member, Nonmember" (2) and "Yes Member" (1). That is a mis-mapped
column — most likely a membership answer that landed in the wrong field during the original
import.

Casting that to a boolean would have **manufactured a legal permission out of the word
"Member"**. Consent to text somebody is exactly what must never be inferred. It is preserved
raw as `legacy_sms_field_raw`, with a column comment stating plainly that it is not consent
and must never be read as permission to text anyone.

The overlapping fields were checked rather than assumed equivalent: `target_markets` 437 vs
`markets_of_interest` 434, `referral_source` 357 vs `found_us_via` 353. Gaps backfilled.

Verified after the merge: **41 of 41** and **6 of 6** preserved.

## Retired, not dropped

Checked before acting: no foreign key references it, no view or function reads it, and the
front end and edge functions mention it **zero** times.

Renamed to `zz_retired_legacy_masterspaces_intake_20260806` rather than dropped. The
ambiguity ends immediately, and a rename is reversible with one statement. Dropping is not.

## The rule going forward

The owner has **700+ more historical clients** who are no longer in the space. When those
arrive they belong in `client_files` **with a status**, not in a second table — or this
exact ambiguity comes straight back.

`client_files` is the source of truth. **475 files, 461 with no platform account.**

# Sixth sweep: what the investor table actually contains

## 34 investors is not 34 clients

Twenty investor accounts have no client file. Sorting them out:

- **4 are test or placeholder accounts**, all `is_active = true`: two named "Big test", plus
  `pending-473a@placeholder.com` and `elena.barbeau@placeholder.com`.
- **Several are staff, not clients** — the owner, an engineer, a trainee AM, and a Success
  Manager who has since resigned. They sit in `investors` and are counted as investors.
- The rest look like genuine clients who simply predate the client-file record.

So any figure quoted as "34 investors" overstates the client base. Worth knowing before it
appears in front of anyone.

## Three real properties are attached to fake accounts

This is the one that matters. **Three of the platform's nine portfolio holdings** belong to
`@placeholder.com` accounts:

| Property | Rent | Owner of record |
|---|---|---|
| 200 Creek Ridge Dr, Round Rock TX | $3,500 | "Portfolio Investor (Pending)" |
| 2101 Firebird Lane Unit 15, Myrtle Beach SC | — | "Portfolio Investor (Pending)" |
| 312 69th Ave N Apt 301, Myrtle Beach SC | $2,800 | "Elena Barbeau" |

Real units, real rent, no real owner record.

**Two consequences:** portfolio figures include holdings with nobody behind them, and
`@placeholder.com` cannot receive mail — so anything sent to these accounts **hard bounces**,
and hard bounces damage the sending reputation of the entire platform.

**Deliberately not guessed at.** There are plausible matches in the client files — Round Rock
and Myrtle Beach both appear there, and one client's file even mentions a "Unit 301". But
assigning a property to the wrong client is worse than leaving it unassigned, and an
inference that looks obvious is exactly how a wrong answer gets stated confidently. That
mistake was already made once today with the per-city launch numbers.

Penny now surfaces all three by address in `penny_attention`, so a person who knows the deals
decides.

# Investor portal — first pass, 9 August 2026

## A client could not change their own password

`change_password` did not exist. Neither did `update_profile` or `logout_all`, so account
settings and "sign out everywhere" were dead buttons.

`investor-session` **already implemented** `update_profile` and `logout_all` — but
repointing the UI at it would have **broken** those screens rather than fixing them, because
`investor-session` validates a `session_token` and the callers send `investor_id`. Same
name, different contract.

**The fix was not to loosen the server.** Accepting a bare `investor_id` would let anyone
edit anyone's profile by guessing an id — worse than a button that does nothing. The
handlers validate a session token, and the three callers now send the token they already
hold.

`change_password` requires the current password (without it, a stolen session could lock the
real owner out), refuses a password identical to the current one, and **ends every other
session** — changing a password because you think somebody has it is pointless if their
session stays alive.

## The deploy verifier cried wolf

The Deploy step reported failure twice, then succeeded on the third attempt — and the
*verification* step then failed. **The deploy was fine.** Fetching the deployed source
directly showed version 44 with all three handlers present, including their distinctive
strings.

So a green deploy was reported as a failure. That is the same class of defect this platform
keeps producing, in the tool built to catch it: **a check that reports a problem where there
is none teaches people to ignore it**, which is how a real failure gets waved through later.

Not yet diagnosed — the annotations carry no detail beyond "exit code 1". Recorded here
rather than left as folklore about "flaky deploys".

## The deploy verifier — one bug found and fixed, one still open

**Fixed:** the literal extractor's single-quote pattern ran from the apostrophe in
`"member's"` to the next apostrophe several strings later, producing seven captures that
were never literals — `, description: "The full email body in Penny` and similar. None
appear in the deployed source because none were ever strings, so a correct deploy reported
"7 expected strings are NOT in the deployed source". Captures containing the other quote
character are now dropped. **169 literals checked → 162 real, zero false missing.**

**Still failing, cause unknown.** With the phantoms removed the step still exits 1, and the
annotations carry no detail beyond "Process completed with exit code 1". GitHub's log API
returns 403 from here, so I cannot read the step output.

**The deployment itself is correct** — confirmed by fetching the deployed source directly:
version 62, all 62 tools present including `credit_requests`, `decide_credit_request`,
`credit_picture`, `claim_alert`, `team_readiness` and `my_sop`.

So the current position is: **deploys are landing correctly and the verifier is reporting
failure anyway.** That is stated plainly rather than treated as flakiness, because a check
everybody learns to ignore is worse than no check — and this one exists to catch "what
deployed" diverging from "what you wrote", which is one of this platform's worst failure
modes.

**Next step for whoever picks this up:** read the raw step log in the Actions UI. The
likeliest remaining cause is `supabase functions download` failing or returning something
unexpected for large functions, since the step overwrites the repo copy with the downloaded
one before comparing.
